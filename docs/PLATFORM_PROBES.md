# Platform probes

Measured on 2026-10-11 between 09:21 and 09:27 UTC on the event workspace with `python tools/probe_platform.py`. Raw reports: `docs/probes/20261011-092221.json`, `-092330.json`, `-092443.json`, `-092622.json`. Each run used one practice customer (PUB-01) and a few chat turns on a small workflow in the slot `probe`. Ordinary functional calls only.

The first two runs were faulty probes, not platform findings: the comparison did not strip a leading space the model adds to an argument, and the first message of a chat only triggers the opening line. Both were fixed before the results below were taken.

| Question | Observed | Evidence | Consequence in the builder |
|---|---|---|---|
| Does an exception in a pre-hook stop the HTTP request? | Yes. No ledger entry, a `function_call_start` event without a request, no `function_call_complete` | run 092443 and 092622, chat `DOB BLOCK-RAISE` | `block_mode: raise` |
| What does the agent read after that exception? | The exception message. The agent answered with the two words the message told it to say | run 092622: reply `pineapple seven.` | The refusal reason and the next step travel in the exception text |
| Does the post-hook run after a stopped call? | No | no post-hook marker in those results | Refusals are counted in the pre-hook |
| Does an empty URL stop the request? | Yes, with no event at all. The agent gets nothing it can act on | run 092443, chat `DOB BLOCK-URL` | Not used |
| Does a pre-hook's rewrite of URL and body take effect? | Yes. The ledger shows `get_account` in place of `verify_identity` | run 092443, chat `DOB BLOCK-REDIRECT` | Kept as a fallback mode only |
| What happens when the bank answers with an HTTP error status? | The agent gets a bare tool error (`API request failed: ...`). The post-hook does not run, nothing is mapped, and the variable written by the pre-hook is still there when the next call starts. Seen for the scripted failure of PUB-10 (`{'ok': False, 'error': 'service unavailable, nothing was recorded'}`) and for a gateway error page of the bank's host | practice call `74d7a0c2-...` (simulation of 10:27 UTC), chat call `d599730b-...` | A failed tool call cannot be counted or answered in its own post-hook. The next pre-hook finds the unanswered `create_promise` and counts it as a failed try; the fixed prompt text tells the agent that a bare error means nothing was done and the tool is called again once. Before this was seen (found on the event afternoon), failures were never counted on the platform and the retry rested on the prompt alone |
| Can a post-hook fail to run although the request reached the bank? | Yes: `Failed to reach snekbox: [Errno 104] Connection reset by peer`. The bank had recorded the promise | chat call of 14:37 UTC and practice call `79a9577b-...` | Same handling as a lost answer: the retry is refused by the bank as a duplicate, which now counts as recorded |
| What happens when the agent sends several tool calls in one message? | They run at the same time: every pre-hook has run before the first answer is handled. A variable written by one pre-hook is overwritten by the next before the first post-hook reads it | practice simulation of 14:57 UTC, call `1877ee54-...`: three `create_promise` calls within 0.3 s, two results attributed to the same product | State must not depend on one pre-hook variable per call. The runtime takes the bank's own answer as the truth for duplicates and reads the call's own request in the post-hook when it is there |
| Do variables written in a pre-hook persist? | Yes, also when the hook then raises or blanks the URL | `probe_pre_seen`, `probe_note` in later variable tables | The pre-hook passes its verdict and normalised arguments to the post-hook |
| Do variables written in a post-hook reach routing? | Yes, both a direct `vars` write and a field injected into `data` and mapped | run 092622: route to `account` on `probe_identity_direct` and `probe_identity` | Both writes are emitted |
| Does a change to `result` in the post-hook reach the flattened `<tool>_response.*` variables? | Yes | `verify_identity_response.data.probe` | Not relied on |
| Where are the tool arguments during the post-hook? | Not there yet. `<tool>_args.*` holds the previous call's arguments at that moment | run 092622: `arg_keys` empty on the first call, stale on the second | The post-hook never reads them |
| In which shape does a mapped list arrive? | It does not: the mapped variable is unset. The flattened keys `account_response.data.products.0.<field>` are set | run 092622, code node report | Products are rebuilt from the flattened keys |
| Does a prompt see a variable changed during the call? | Yes, in the next turn | run 092622: the agent answered `mango nine` | Fact blocks may be written late |
| Does an initial code node run in the chat route? | No | `setup` marker unset in every chat | The setup also runs on demand in the first hook; the chat smoke turn sees no calendar |
| Does an initial code node run in a simulation? | Yes | practice run 092840: `setup` executed before the opening line | The calendar facts exist from the first turn in scored calls |
| Sandbox | Nested functions, function-local `import json, re, datetime`, `isinstance`, `sorted`, `any`, `all`, `set`, `enumerate`, `%` formatting, `float`, `date.fromisoformat`, `re.match` all work | `scope` field | The runtime runs as written |
| Workflow size | A 505 KB workflow passes dry run, save, publish and readback with no difference | build 092840 | No size reduction needed |
| Readback | The platform adds `"description": ""` to every `response_mapping` entry and changes nothing else that was sent | builds 092819 and 092840 | The readback comparison ignores that addition |

Also seen: the agent model often prefixes an argument with a space (`" 4471"`), and after one tool result it can stop calling a tool when the result's instruction only tells it what to say. Arguments are trimmed in the pre-hook, and every `what_to_do_next` names the next tool when one is due.
